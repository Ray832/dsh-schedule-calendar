# v1.3.0：手动标记完成、提醒三档、模型改日程

## 目标

用户提了三件事：

1. 提醒弹出来时可以标记完成，但**面板里没有地方手动勾**——要能手动标记完成/取消；
   并且给模型一个标记完成的工具，`calendar_list` 要带上完成状态。
2. 重做提醒档位：短期按"提前 X 小时 Y 分钟"细分（0-24 / 0-60）、中期按"提前 X 天"（1-15）、
   长期可选每 1/3/5/7 天反复提醒。提醒弹出后可选：标记完成 / 关闭提醒 / 稍后提醒（重新设档）。
3. 让模型能改日程的设置（时间、地点、备注、提醒），并要求判断"改造 add 还是新开工具"。

  `snooze` 允许长延时（把 snoozed 目标当成 age 基准，不再被 30 分钟清理掉）。
- `src/tools.ts`（重写）：五个工具 + 共享的档位 schema + 审批门四分支（add/update/complete/delete）；

## 为什么

- **档位而不是分钟数组**：一个数组只能表达"响几次"，表达不了"每几天响一次"；而固定 chip 也表达不了
  "提前 1 小时 40 分钟"。详见 ADR 0007。
- **分钟数组仍然保留**：引擎和 ICS 导出都只认分钟，改造它们成本高、收益低；让档位做唯一真实来源，
  数组在保存时派生，是成本最低的一致做法。
- **旧事件不自动迁移**：旧的 `[10, 0]` 有两个提醒时刻，档位只能表达一个。自动迁移会静默丢一个；
  保留原数组直到用户重新保存，用户能看见自己在改什么。
- **新开 update / complete，不改造 add**：见 ADR 0008（upsert 会诱导模型重发整条事件而重复创建；
  一个意图一个 description 才有明确的触发词）。
- **完成状态只有一条写路径**：`calendar_update` 不开放 `done`，避免两个工具写同一字段。

## 踩到的坑

1. **长期档的提醒永远不会触发**：引擎原本只把 `now + 1h` 内的 occurrence 展开，而 7 天档的提醒要提前 7 天响，
   那时事件还在窗口外，压根不参与扫描。改成 `now + 15 天`（等于档位上限）后正常。
   ——这个 bug 是写 `tests/notify.mjs` 的梯子断言时才暴露的，说明"先写测试再改引擎"是对的。
2. **`snooze` 超过 30 分钟会被清理**：`prune` 用 `firedAt` 算年龄，`snooze` 只改了 `snoozedUntil`。
   现在 `snooze` 把 `firedAt` 设为目标时刻，长延时不再被误删（测试里用 120 分钟验证）。
3. **工具返回值与 schema 不一致**：`calendar_update` 的 output 要求 `changed`、`calendar_complete` 要求
   `done`，但 handler 只返回 `{id,title,start,end}`，测试直接报 `undefined`。修法是 execute 里补齐派生字段，
   而不是放宽 schema。
4. **`normalize` 里的 settings 迁移写错**：`{...base.settings, ...doc.settings}` 之后 `defaultReminder` 永远存在
   （来自默认值），迁移分支成了死代码。改为读 `rawSettings.defaultReminder` 判断。
5. **`docs:check` 的 slug 生成**：`log:new` 把 "v1.3.0" 变成 `v1-3-0`，与本项目其它日志的英文 slug 不一致，
   手动重命名并同步 INDEX 即可（脚本本身没问题）。

  `event.setDone` 往返；`settings.update` 派生 `defaultRemindBefore`。
- `npm test`（docs:check + 7 套件）全绿；`tsc --noEmit` 通过。

## 遗留

- 重复事件的 `done` 是整条共享的，勾掉一场等于勾掉整条。要做"只完成这一场"需要 occurrence 级状态，
  属于数据模型变更，先写 ADR。
- 提醒卡里的"稍后提醒"只做**本次延后**，不改事件的档位；要改档位请打开该日程编辑。
- `calendar_search` 仍未做。
